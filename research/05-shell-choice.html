Desktop UI shell choice — decision report

Research pass 2026-11-22. Read-only: no toolchain installed, no project scaffolded, no repo modified. web_search/web_fetch returned HTTP 402 (no credits), so every number below came from crates.io/api/v1, registry.npmjs.org, api.github.com, raw.githubusercontent.com, and one blog article fetched with curl. Versions and download counts are as of this session; each carries its date.

0. Recommendation

Tauri 2.x (stable 2.12.7, 2026-11-18) with the Rust runner as a child/embedded process and the transcript served to the webview over a loopback HTTP/SSE endpoint, not Tauri IPC — the same shape all three reference apps converged on, and the one that keeps a browser/phone client free. Memory is not the reason to pick it: the measured Electron→Tauri idle delta is 26.5 MiB (59.5 vs 86.0 MiB), ~1 % of the 0.9–7.5 GB the 3–5 agent subprocesses will consume. Change it if the §7 Linux spike reproduces WebKitGTK breakage that we must ship through (xterm.js WebGL, WEBKIT_DISABLE_DMABUF_RENDERER abort, the font-weight-100 bug) — then take Electron, because the React UI is byte-identical either way and the runner is the same Rust process in both.

What those lines buy, from the dependency lists actually in each package.json:

  • orca: @xterm/xterm + addon-webgl/fit/serialize/search/image/ligatures/web-links + @xterm/headless, shiki, react-markdown, @tanstack/react-virtual, @monaco-editor/react, diff.

Read this as: nobody in this space writes their own renderer. Three independent teams, three licences, same shopping list. The 37 k–98 k prod lines are not markdown rendering — they are the behaviour around it: streaming deltas into a stable layout without re-mounting highlighters, tool-call rows that expand into diffs, per-agent message shapes, scroll anchoring while tokens arrive, selection across virtualized rows, and the composer.

3. Terminal emulation

Four real options, all verified:

  1. xterm.js in a webview — @xterm/xterm 6.0.0 (2025-12-22), 21.4 k★, pushed 2026-11-22, 344 open issues, addons for WebGL rendering, fit, search, serialize, images, ligatures, plus @xterm/headless for server-side scraping. This is what VS Code, orca and cloudroom ship. Nothing in Rust is close in completeness: scrollback, selection, mouse modes, IME, hyperlinks, bracketed paste, resize/reflow.
  2. alacritty_terminal 0.26.0 — the real parser/grid, published and used by both egui_term and iced_term. There is no wezterm-term on crates.io (404); wezterm's termwiz 0.23.3 exists but last released 2025-03-20. vt100 0.18.1 (21.4 M dl) parses but is not an emulator front-end.
  3. Roll your own on alacritty_terminal — you supply glyph atlas + wgpu/canvas drawing, cell damage tracking, selection, mouse reporting, key encoding, IME, search, and reflow. orca's terminal-pane is 79,363 prod lines and that is with xterm.js doing the emulation; it is spending those lines on PTY transport, remote runtime, tab/session state and UI. A native pane is a multi-month item, not a week.
  4. Embed a separate terminal app — loses the point.

Practical choice: with a webview the terminal is a solved, boring dependency. With any native toolkit it becomes one of the two or three hardest parts of the product — for a developer tool, that is the worst place to spend novelty budget.

Two Linux notes that matter for a developer tool: Tauri's Linux prerequisites require libwebkit2gtk-4.1-dev (Ubuntu 22.04+) and therefore the library is a host dependency, and webkit2gtk-rs is mid-migration to v3.0 (PR #16612, 2026-11-22), i.e. a dependency bump is coming whether or not you want it.

5. Cost to build the v1 UI

Order of magnitude, derived from the prod line counts above plus the crate inventory. "v1" means: one transcript per thread, streaming, markdown + code highlight, unified and side-by-side diff, file tree, terminal pane, context ledger — no plugins, no settings matrix.

Option Lines we write ourselves Calendar (1 senior) What we must build that nobody sells us
Tauri 15 k–25 k TSX/CSS, plus the Rust runner 6–10 weeks to a usable v1 transcript row model, scroll anchoring, diff wrapper, ledger panel. Markdown, highlighting, diffs, terminal, virtualization all bought.
Electron same 15 k–25 k, same components 6–10 weeks identical to Tauri — strictly a superset cost (bigger binary, Chromium majors)
egui 45 k–70 k 4–6 months markdown layout + link handling, inline code/code blocks with measured line widths, text selection across widgets, clipboard of rich content, diff view, terminal pane, drag-select rows, theming beyond egui's look
iced 60 k–90 k 6–9 months all of egui's list, plus virtualization, plus accessibility (no accesskit at all), against a toolkit that shipped once in the last 12 months
Slint 35 k–55 k 3–5 months markdown/rich-text view (no crate exists), diff view, terminal pane; UI panels are the pleasant part, the transcript is the expensive part
GPUI unbounded not planable the framework itself, since 0.2.2 will not compile from crates.io as documented

The asymmetry is the whole argument: 37–98 k prod lines exist in the reference apps because the web stack makes the hard parts additive. In a native toolkit the same features are subtractive — each one removes weeks and adds permanent ownership.

6. Risks and unknowns

  1. Linux is the actual risk, not memory. Three verified WebKitGTK facts, each dated: tauri#14286 (open, 2025-10-12) — font weight is offset by exactly 100 on WebKitGTK, text renders bolder than in any browser, CSS computed values are correct; tauri#16226 (open PR, 2026-10-07) — on Wayland with NVIDIA proprietary drivers or compositors without explicit sync, webkit2gtk 2.44 enables the DMA-BUF renderer and GDK calls abort(), which "no Rust error handling or panic catching can survive"; only mitigation is WEBKIT_DISABLE_DMABUF_RENDERER=1. Third: devtools is a cargo feature, so release builds ship without an inspector unless you opt in.
  2. Tauri startup is not faster than Electron in the one controlled measurement: first frame 377 ms vs 326 ms. And in 4 of 50 Tauri launches the first frame was held 8–80 s after the script ran, because the window started hidden — a real hazard for tray/restore flows.
  3. Tauri IPC is not the transport for a token stream. The same benchmark: 50 MiB in 112 ms via ipc::Response, 279 ms via serde, and a Channel resolves invoke() before its chunks arrive (0 chunks received in all 9 calls). Batch deltas, or use loopback HTTP/SSE — which is what gives us browser/phone reuse for free.
  4. Tauri 3.0 lands inside our horizon (alpha.6 2026-11-06; milestone "3.0" has 11 open issues; "2.13" has 14). Budget one migration. 2.x will stay supported but the ecosystem will fork attention.
  5. Electron's hidden cost is the 8-week Chromium major, and the refs demonstrate it: orca pins 43.8.10, t3code 44.10.1, cloudroom 44.11.2, while 45.4.1 is current. Three teams, all behind.
  6. Attribute/reuse trap. Slint's royalty-free licence requires shipping AboutSlint in an About dialog or a "Made with Slint" badge on the download page; the licence also forbids exposing the toolkit's APIs. Fine for us, but it is a permanent product constraint, and GPLv3-or-commercial otherwise.
  7. Unverified but load-bearing: whether xterm.js's WebGL addon works acceptably under WebKitGTK (canvas fallback exists, but the terminal is where developers notice latency); whether egui's text selection and IME behave well enough for a chat composer. Both are §7 tests, not reading.

7. A 30-minute spike that would settle it

One page, one binary, on the machine we actually ship to (Ubuntu 24.04, Wayland, and the NVIDIA laptop if that is a target; repeat on macOS). Do not build a chat app — build the four primitives.

  1. npm create tauri-app@latest (vanilla TS), 2 min.
  2. One page, four panes: (a) a fake transcript that appends a 60-char markdown delta every 16 ms for 20 s, with shiki highlighting a code block that is re-highlighted each frame; (b) xterm.js + addon-webgl running top for 10 s from a Rust Child; (c) a 2,000-line side-by-side diff from react-diff-view; (d) a 10,000-row virtualized list from @tanstack/react-virtual, scrolling.
  3. Measure with ps -o rss= --ppid over the process tree every second, and performance.now() deltas into a log; print p50/p95 frame time.

Pass criteria (all must hold): total RSS < 400 MB with 3 idle node children running; p95 frame time < 20 ms during (a) and (d); xterm WebGL context created and key echo latency < 50 ms; no GDK protocol-error abort across 10 launches; text weight matches the same HTML in Firefox within one screenshot. Fail any of (b) or the launch test → Electron, same day, same React code, zero UI rewrite.

Add 10 minutes: repeat step 3 with node × 3 at 1 GB each, to confirm the shell's RSS does not scale with agent memory (it should not; if it does, our process model is wrong, not the shell).

8. What I could not verify

  • Memory for an app of our shape. The only controlled Electron↔Tauri measurement I found is an empty page plus a JSON payload trickle (Woliński, 2026-11-22, Tauri 2.12.5 vs Electron 45.2.3, macOS 27.2, M1 Pro 32 GB). No published measurement covers a chat app with a real React bundle, highlighters and a terminal — and none covers Linux or Windows (the author says so explicitly). The 26.5 MiB delta is therefore a floor, not our number.
  • Any Linux/Windows memory figure for either shell. Nothing citable exists that I could reach.
  • xterm.js under WebKitGTK, and whether the WebGL addon survives the DMA-BUF path.
  • egui / iced / Slint text selection, IME, and copy-with-formatting semantics — not verifiable by reading; needs hands on a build, which this pass was not allowed to do.
  • Whether gpui 0.2.2 actually builds from crates.io (gpui_platform missing suggests not). I did not compile it.
  • Whether Tauri's .AppImage/.deb bundles carry libwebkit2gtk-4.1 or require it on the host. The prerequisites doc requires it for development; packaging behaviour is unconfirmed.
  • Slint's rich-text ceiling — no markdown crate exists, but I did not test how far Text with spans gets us.
  • Real LOC for our own v1. §5 is an order-of-magnitude estimate scaled from the reference repos, not a bottom-up plan.

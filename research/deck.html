Verdict / if you read one page

Five findings that change the plan

01
You cannot ship a pure web app.
Agent CLIs need a repo, a shell and the user’s login on the machine that runs them. All three ship a runner: t3 a Node server, cloudroom a Mac daemon, orca Electron main. t3 apps/server · cloudroom host-daemon · orca src/main
02
“Threads that see each other” is unsolved, everywhere.
All three have pull-based, point-to-point tools. None has ambient shared context, peer discovery or a push subscription. Each documents the absence explicitly. 01 §10.2 · 02 §10 “no blackboard” · 03 §10
03
The provider adapters are the project, not a feature.
orca carries 45 hand-tuned PTY records, 17 ACP dialects and 23 hook installers. cloudroom carries 14 local + 13 cloud adapters and a parity harness. t3 carries 11 protocol bindings. 02 §4 · 03 §4 · 01 §4.3
04
The model is the scheduler. Nobody kept the engine.
t3 injects an orchestration contract into every session. orca retired its programmatic coordinator behind a migration fence. cloudroom’s only fan-out is a workflow script. orca orchestration-contract-fence.ts · cloudroom plugins/workflows
05
Copy ten shapes. Fork nothing.
1.29M / 3.6M / 483k lines, each with a load-bearing toolchain and a closed control plane. The reusable part is the design of five files per repo. 01 §13 · 02 §13 · 03 §13

Structure / the one diagram that decides your stack

The browser is a view. The runner is the product.

Every one of the three ends up here, from three different starting points. The runner owns process lifecycle, state, credentials and crash recovery. The client owns nothing but rendering and intent.

Why it exists
Five threads = five processes
All drivers but Codex refuse to attach two app threads to one session. Budget 300 MB–1.5 GB and 5–15 s cold start per thread. 16 GB laptop, 3–5 threads.
Consequence
Parking is a feature
Freeze a thread, keep history, resume it later. cloudroom models 17 session states for exactly this. “running / idle / error” will not survive contact with real use.

What the client must not do

Hold credentials, hold canonical state, or replay history to reconstruct a view. All three moved this to the runner for the same reason: a browser tab is disposable.

What the runner must guarantee

One transaction per command: events, projections, receipt and outgoing effects. That is the only way “queued / running / waiting / done” stays honest when a provider dies mid-turn.

What optional means here

Teleporting a live session between machines is the hardest feature in the set. It needs a control plane that is not in any of the three repos.

Convergence / treat these as decided

Eleven things all three built the same way

Each item below was arrived at independently by at least two of them. That is what makes it a specification rather than an opinion.

01

One normalized event stream per turn. Adapters translate; the UI never learns a provider name. 18 event variants, 27 delta kinds, per-agent dialect mappers. 01 §4.2 · 03 §4.2 · 02 §4

02

Capabilities are declared, not probed. Missing features degrade by policy, never by if (provider === …). 01 §4.1 · 03 §4.5

03

One thread, one process — except Codex, the only driver that attaches several app threads to one session. 01 §13

04

Worktrees to isolate; shared checkout as opt-in. Isolated agents cannot see uncommitted work. The answer is always “commit, then share via git”. 01 §10.1 · 02 §10 · 03 §10

05

The agent’s own transcript is the record. orca reads each CLI’s JSONL store rather than keeping a rival copy; cloudroom refuses to fabricate missing history. 02 native-chat/transcript-reader.ts · 03 §4.4

06

Credentials never leave the runner. “Tokens never pass through the GUI or core API.” API keys only via secret providers or env. 03 §4.6 · 01 §4.5

07

Idempotency, and an honest unknown. Request id plus payload hash plus caller fingerprint. Uncertain work is never blindly retried. 03 §12 · 02 §5 · 01 §12

08

The app injects the collaboration contract. t3’s instruction file is the block in the prompt I was running under. orca writes the worker preamble into the first message. 01 §10.1 · 02 worker-dispatch-preamble.ts

09

Bounded reads of another thread. ~30k chars per call with cursors. A transcript dump into a prompt is the fastest way to burn a context window. 01 toolkits/thread/tools.ts

10

Structured results beat prose. Schema-constrained output; a reported failure can never be recorded as success, in any of the three. 01 t3_submit_output · 03 workflows · 02 worker_done

11

Disk and durability guards are mandatory. One burned 50 GB in days and now ships a reserve file. Multi-agent is an IO workload, not a UI workload. 03 §12 · 01 §6

—

The corollary: if we deviate on any of these, the reports suggest we will rediscover it the expensive way — as a bug that looks like a provider problem.

The reading

Both mechanisms are needed and they are not substitutes. Tools are how an agent expresses intent. Typing a pointer into a terminal is how you deliver anything to an agent that has no API. One gives you expressiveness on five providers; the other gives you coverage on forty.

The reason all three abandoned a programmatic coordinator is the same in each report: real work arrives out of order, and a scheduler that cannot ask a question stalls. An agent that can ask is slower and survives.

Product / what is actually yours to build

Four primitives nobody has

“Many agents in one window” is done. “Threads that talk” is done, point-to-point. What is missing is the layer that makes five threads behave like one team without a human playing messenger.

1 · A project context ledger

Decisions, constraints, changed files, open questions, who owns what. Every turn’s preamble carries a digest; any thread appends with one tool call; the user can read and edit it. Plain files, greppable — not a vector database.

Replaces: “the coordinator remembered to write it down” (02 §13)

2 · Turn completion as a structured push

Not a transcript. {thread, status, verdict, filesChanged, summary}, delivered to interested threads as a wake plus a compact digest.

Combine: t3 outputSchema, orca mailbox delivery, cloudroom turn reports

3 · Review rounds as data

“Claude writes, Codex reviews, Pi documents” is a pipeline with a verdict, not three chats. Model the round below instead of hiding it in prompts and mail.

Closest primitives: orca diff comments, worker_done --outcome

4 · Peer discovery inside a project

“Who else is working in this repo, on which files, since when.” Needs a registry none of the three has. Start with awareness only — a warning, not lock arbitration.

orca is explicit: no locks, no ownership signal (02 §10)

Why files and not a shared memory service. All three converged on files plus mail for the same three reasons: it survives a context loss, it works for any model, and a human can audit it. A vector store would be novel in this set — a warning sign, not an argument.

Why not start with arbitration. Merge arbitration between concurrent agents is a research problem. Awareness (a warning in context) is a day of work and removes most of the pain.

A review round, stored as state instead of as chatone object · four states · one verdict
state 1

Claude writes. The changed files and a diff pointer are recorded on the round, not in a message.
state 2

Codex reads the diff pointer, returns a verdict plus findings — schema-constrained, not prose.
state 3

Findings land in the writer’s context as an object. Each one is resolved or explicitly declined.

Risk / what the reports could not soften

Five things that will bite

01
Forking is not on the table.
1.29M, 3.6M and 483k lines. One has Effect as a hard toolchain, one has Electron plus native node-pty plus an xterm beta, one has two runtimes and no control plane. Read for design; copy short shapes with attribution.
02
Every cloud feature in all three is closed.
t3’s hosted app and relay, orca’s connector and artifact services, cloudroom’s entire web/ — accounts, sandbox provisioning, credits, child and relay endpoints — are referenced by name in the code and absent from the repos. They are products, not blueprints.
03
Two agents on one account can sign each other out.
Refresh-token rotation conflicts are documented for Kimi and Codex. Run five agents under one login and you inherit that class of bug — plus usage limits that must be classified distinctly from failure, not as a generic error.
04
Docs drift faster than code in this category.
orca’s hand-written skill guides are more accurate than its docs; t3 says pin a commit because the repos move. Any spec we write must cite file paths, not prose, or it will be stale within a month.
05
“All subscriptions” is partly a legal question.
One harness refuses Claude plans on principle. Vendored licences are not uniform. Expect terms-of-service review to constrain the provider list independently of engineering effort.

Scope / a position, to argue with

Version one

Small enough to finish, large enough to prove the only claim that matters: that many threads can behave like one team.

Build 8 items

  • Browser UI + one local runner. Node, spawns CLIs, owns SQLite, streams over WS. No cloud runner.
  • One project, N threads. Thread equals one agent session on one provider instance.
  • Three tiers, published: ACP default, native for Claude and Codex, PTY for at most two, labelled beta.
  • Cross-thread tools: read (bounded), search, send (queue or steer), delegate (task prompt only), transfer.
  • The four primitives: context ledger, turn-boundary push, review rounds, peer registry.
  • Transactional run state from day one — command, events, projections, receipts, outbox.
  • Park and resume a thread; disk reserve; idempotent mutations with an honest unknown.
  • Conflict awareness as a warning in context. Not arbitration.

Not yet 7 items

  • Cloud sandboxes, teleport, remote runners, federation.
  • Mobile app and embedded browser.
  • Computer use, org sharing, marketplace.
  • A scheduler, DAG engine or coordinator service.
  • More than about five providers.
  • Merge arbitration between concurrent writers.
  • “Parity with every agent” as a public promise.

Next / six answers before any code

The decisions, and what each one forecloses

1
Whose machine runs the agents?
The user’s laptop means an installer, local credentials, and a runner you cannot debug remotely. Yours means compute cost, tenancy, and the cloudrunner you just deferred. This is the business model, not a technical detail.
2
ACP-first or native-first?
ACP gets you ten agents in a week with weaker approvals. Native gets you fork, rewind, subagents and honest permission prompts for the two agents that carry the demo. Native-first is slower but sells better.
3
Coordinator agent, tool surface, or board?
t3’s tools, orca’s coordinator, cloudroom’s tasks each produce a different product. Tools plus a board is the most defensible; a coordinator is the fastest demo. Pick one as primary and let the others be features.
4
One checkout or a worktree per thread?
Shared is roughly ten times simpler and fine for a write / review / document split. Two writers on one branch need isolation. You can start shared and make it a per-thread toggle.
5
Ledger as committed files or app state?
Files survive everything, greppable, reviewable in a PR, and work with every agent’s tools. App state is cleaner to present. Files first; a UI over them later.
6
What is the one demo that proves it?
Probably: Claude writes, Codex reviews with a verdict, Pi documents the diff — and the review lands in Claude’s context without a human copy-pasting. If that runs, the product is real. Everything else is packaging.

My recommendation: local runner, tool surface plus a small board, ACP default with native Claude and Codex, shared checkout with an opt-in worktree, ledger as committed markdown, and the write → review → document round as the only end-to-end flow in v1. Roughly one quarter of work, with a demo in week three.

Rationale for each recommendation is in 00-synthesis.md §9 and §3.3. Disagreement is welcome — but then one of the six above changes, and the cost of that change is in the corresponding report section.
Closing / the answer to “are they similar?”

Yes — three solutions to one problem, agreeing on the skeleton and disagreeing on how much structure an agent will accept.

They agree on project → thread → adapter → one normalized event stream → transactional state → a client over WS or SSE. They agree on worktree isolation, credentials staying on the runner, and coordination as tools plus mail plus an injected prompt contract, with the model doing the scheduling.

They disagree on how much they demand of the agent — a rich tool API, a mailbox typed into a terminal, or a plugin bridge — which is really a disagreement about which agents you can support at all.

The unsolved part — and therefore the only defensible core — is shared context between threads that is default-on, structured, and readable by both humans and agents. After that, review rounds modelled as data rather than as chat. 00-synthesis.md §11

Ilvuno v1 brief: security and provider contract

1. Security model

Ilvuno does not sandbox agent processes. Agents are limited only by the permissions their CLI already has. The runner's job is to avoid handing them more access. v1 is single-user and runs on one local machine.

The user and the runner are trusted. The repository and the agent processes are not, because a hostile file in the repo can inject prompts. Provider CLIs are trusted but opaque, so their output is treated as data.

Rules the runner enforces:

  • Provider credentials never enter an agent's environment.
  • Each worker gets its own worktree. Workers never switch branches or touch main.
  • Merges happen only in the runner, and only after an accepted round.
  • Scope is checked at dispatch and at report. Out-of-scope diffs are shown and block pass, but this detects problems rather than preventing them.
  • Every command and effect is journaled with a request id.

Known limits: there is no network allowlist, so an injected agent with shell access could send files out. The runner gives no protection against a malicious provider CLI or a root-compromised machine. Malicious skills or MCP servers are outside its control.

Act on these:

  • Do not give workers a git remote. Do not allow force-push, branch -D, or reset --hard by workers.
  • Pin adapter versions fetched with npx -y, and record the resolved version in the journal.
  • Keep the human gate on. Keep permission mode default. Never use bypass permissions.
  • Review the context size shown per thread, and trim injected skill descriptions.
  • If credentials may have leaked, rotate them at the provider. Ilvuno does not store them.
  • On an incident, run ilvuno run freeze <run>, then read the journal.
  • Keep reports and journals local. They can contain source code and possibly secrets.

2. Provider contract

The contract covers what an adapter must implement and what the runner promises it. v1 has two adapters: claude, which uses native stream-json and the control protocol, and acp, which points at any agent's ACP command. The core rule is zero first-party privilege. Anything claude needs that the ACP adapter cannot also get must go into the shared capability struct, or it does not exist.

The adapter is a translator, not a decision-maker. It never writes the database, never decides a round is done, and never retries a turn on its own. If it cannot answer, it emits unknown and the runner decides.

Key terms:

  • Commands (runner to adapter): spawn, session_open, session_resume, prompt, permission_reply, interrupt, park/unpark, shutdown. Each carries a request_id, and resending the same id must not start a second turn.
  • Events (adapter to runner): eleven kinds, including text_delta, tool_call, permission_request, usage, turn_finished, and raw. Anything unmodelled goes into raw.
  • Capabilities are declared, not probed. The runner greys out what is absent and never imitates a missing feature.
  • Error classes: spawn_failed, auth_required, usage_limit, turn_failed, protocol, unknown. Adapter death counts as turn_failed with reason adapter_died.
  • Prompts are versioned in code and injected every turn. The journal records the version injected into each task.

Act on these:

  1. Send control_request{initialize} before any Claude turn. Without it, every tool is silently denied.
  2. Set "mode": "workspace-write" on ACP provider entries. Otherwise permission requests are bypassed. ACP answers by option kind, not position.
  3. Do not treat /tmp as a security boundary. It is writable in workspace-write mode by default.
  4. Use absolute paths for runner commands in worker preambles. A Codex login shell's PATH differs from the runner's.
  5. Treat acp:* as tier 3 unless it has been tested.
  6. Do not ship PTY scraping in v1. An agent without ACP or a protocol is labelled, not faked.

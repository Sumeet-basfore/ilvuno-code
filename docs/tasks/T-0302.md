# T-0302 — Overlap and proximity analysis

Milestone: M3 · Estimate: 1 d · Owner: B · Provisional: no

## Goal
Two cheap, deterministic findings that explain most conflicts before they happen: which files two
streams both touch, and where edits land close enough to be risky but clean.

## Dependencies
T-0301. `INT-201`, `INT-202`.

## Allowed file scope
- `internal/analyze/overlap.go`, `internal/analyze/proximity.go`
- `internal/analyze/testdata/`

**May not touch:** `internal/verify`, `internal/cli`.

## Implementation outline
1. Per source: `diff --name-only --no-renames base..sha` (SHAs only).
2. `file_overlap`: set intersection across ≥2 sources → one finding per file, listing sources.
   Severity warning; never blocking.
3. `proximity` (opt-in): for files with ≥2 sources, `diff -U0` per source, parse changed line
   intervals, report pairs within `window` (default 5) that merged cleanly.
4. Cap output: 200 findings max, then a summary finding with the remaining count (no silent truncation).
5. Deterministic ordering: by path, then by source SHA.
6. Rename handling: `--no-renames` so a rename shows as delete+add (deterministic; documented).

## Acceptance criteria
| AC | Statement |
|---|---|
| AC-1 | `B-01` yields exactly one `file_overlap` naming both SHAs and the file |
| AC-2 | `B-06` with proximity off yields zero findings; with on, exactly one |
| AC-3 | Findings are sorted deterministically (path, then SHA) |
| AC-4 | >200 findings truncates with an explicit summary finding |
| AC-5 | No finding has `severity: blocking` |
| AC-6 | Analysis runs in ≤ 300 ms for 3 sources / 20k files |

## Review checklist
- Is the overlap key path-only (no content hashing that could vary)?
- Does proximity ever claim a conflict? (it must not — it is a warning about near misses)
- Is the finding count cap visible to the reader?

# T-0005 — E-1: merge-tree tuple-conflict spike

Milestone: M0 · Estimate: 1 d · Owner: A · Provisional: no

## Goal
Answer one question with evidence: **can `git merge-tree --write-tree` detect a conflict that exists
only for the full tuple of three branches (all pairs clean)?** This is falsification experiment E-1
and it decides whether preflight can block.

## Dependencies
T-0002, T-0003 (`conflict_triple` fixture).

## Allowed file scope
- `internal/testkit/spike/` (throwaway, `//go:build spike` tag)
- `docs/research/08-e1-merge-tree-tuple.md` (findings note)

**May not touch:** production packages. This is a spike; it must not leak into the product.

## Implementation outline
1. Build the triple-conflict fixture; verify all three pairs merge cleanly with real `git merge`
   in scratch worktrees.
2. Run `git merge-tree --write-tree --name-only <base> <a> <b> <c>`; capture exit, stdout, tree oid.
3. Run the real sequential merge A→B→C; capture the conflict at the step it appears.
4. Compare: does merge-tree's tuple call report the same paths? Does it report a tree oid anyway?
5. Repeat with a 4-branch variant where only the 4-tuple conflicts.
6. Test git 2.38 (floor) via a container or `git --version` check; note behaviour differences.
7. Write the findings note: verdict, exact commands, SHAs, and the implication for ADR-0006.

## Acceptance criteria
| AC | Statement |
|---|---|
| AC-1 | The fixture genuinely has all pairs clean (proved by real merges) |
| AC-2 | The tuple merge genuinely conflicts (proved by a real sequential merge) |
| AC-3 | `merge-tree --write-tree` output is captured verbatim, including exit code |
| AC-4 | A verdict is recorded: `tuple-detectable` or `tuple-blind`, with the evidence |
| AC-5 | If `tuple-blind`, the note states the exact consequence for preflight (demote to advisory) and names the ADR section to amend |
| AC-6 | Spike code is behind a build tag and excluded from `make build` |

## Test commands
```
go test -tags spike ./internal/testkit/spike/... -count=1 -v
git --version
```

## Evidence requirements
Findings note with: commands, full output, SHAs, verdict, implication. This note is a G0 artefact.

## Review checklist
- Is the fixture *really* pair-clean? (the most likely error is an accidental pair conflict)
- Was the real merge done in a throwaway worktree, not the user's tree?
- Does the note distinguish "merge-tree detects" from "sequential merge detects"? (they are different
  claims and both matter)
- If positive, does the note avoid overclaiming: does it say *which* pairs conflict, not just "yes"?

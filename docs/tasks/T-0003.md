# T-0003 — Failure-class fixture corpus (ported SP-1R3 corpus)

Milestone: M0 · Estimate: 1 d (was 1.5 d; re-estimate after S-1) · Owner: B · Provisional: no

## Goal
Every M0 fixture has a name, a failure class and an asserted verdict that the SP-1R3 harness has already
verified, so later milestones point at a named fixture instead of inventing one. The corpus is ported, not
re-invented.

**Not ported** (deferred pending S-1): T-API-2, T-DEP-1, T-DEP-2, T-API-3, T-COMP-1, T-SAFE-1, T-CONF-3,
T-CONF-4 (rename), `stale_base` drift. These need product code to assert.

**Dropped:** `conflict_triple` (tuple conflict). X-08 found no reproducible case, and the tuple check it
tested does not exist (`docs/readiness/02` §2).

## Implementation outline
1. One file per fixture, named by its SP-1R3 ID (`f01_two_clean.go` … `f10_newline_path.go`), so results can
   be cross-checked by name.
2. Each fixture exposes `Spec() forge.Spec` and `Assert(t, repo)`. `Assert` checks the verdict and exit that
   `expected.json` records. It does not reimplement the classification.
3. Read git state only with `--porcelain`, `-z` or `rev-parse`. Never parse human-readable output.
4. `corpus_test.go` is a table over the eight ported fixtures. F8's `Assert` checks that the driver is
   configured and that its marker file is absent. It does not run the driver.
5. Record build time per fixture.

## Acceptance criteria
| AC | Statement |
|---|---|
| AC-1 | Each ported fixture carries its SP-1R3 ID and class from the table above |
| AC-2 | `Assert` for each fixture checks the verdict and exit recorded in `expected.json`, read by the test, not restated from the test's own reasoning |
| AC-3 | F3 and F4 each produce a real conflict (`git merge` exit ≠ 0) at the stated step |
| AC-4 | F7 fails only on the combined candidate, as its spec states. The test verifies that the candidate is red and that each source alone is green |
| AC-5 | Each fixture builds in < 400 ms |
| AC-6 | No TypeScript, npm or network dependency. No configured driver or hook executes during build or assert |
| AC-7 | The F9 fault-injection test exists and fails the cleanup step when the injection is applied (S-1) |

## Evidence requirements
Table: SP-1R3 ID → class → asserted verdict → build time. Plus forge base SHAs compared with `oracle.json`
(T-0002 AC-7).

## Review checklist
- Does each fixture represent its class, or only resemble it? F4 must conflict at step 2, not as a pair.
- Are verdicts read from `expected.json`, not restated in the test?
- Is each ported spec equivalent in intent to `spec.json`? Any difference needs a note in the PR.
- Non-ported classes are added only after a new owner decision (S-1 defers them).

## Implementation notes (2026-11-20)

- Ported: F1–F8 and F10 in `internal/testkit/fixtures/fixtures.go`, each builder reproducing its `sp1.sh` case step for step, including the common base commit that F5, F7 and F8 build on.
- The reference runner (`integrate.go`) follows the oracle: refuse configured executable features before any merge, one `merge --no-ff` per source in a detached worktree, identity `ilvuno`, base commit time, the F7 check on the candidate, cleanup on every path.
- Verified against `testdata/reference/expected.json`: verdict, exit, conflict step and paths, and candidate SHA for every ported fixture; AC-4 by checking each source alone and the combination.
- F9 is a fault-injection test (`TestF9FaultInjectionLeavesOrphanAndExitsFive`), not a corpus entry. The Go suite runs it with the cleanup injected, so the orphan and exit 5 are shown.
- Not ported (S-1 defers them): T-API-2, T-DEP-1, T-DEP-2, T-API-3, T-COMP-1, T-SAFE-1, T-CONF-3, T-CONF-4, `stale_base`.

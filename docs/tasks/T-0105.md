# T-0105 — `doctor`, `init`, worktree discovery

Milestone: M1 · Estimate: 1.5 d · Owner: A · Provisional: no

## Goal
Two commands that make the product legible before it is powerful: `doctor` explains the environment
and refuses to hide problems; `init` writes a config it will not overwrite and proposes real commands
from the repo. Plus read-only worktree discovery with ownership classification.

## Dependencies
T-0101..T-0104. Architecture `12` §8, `05` §2–§3.

## Allowed file scope
- `internal/cli/doctor.go`, `internal/cli/init.go`
- `internal/gitx/worktree_list.go`
- `internal/model/worktree.go`
- `docs/doctor-output.md` (golden sample)

**May not touch:** worktree creation (T-0202).

## Implementation outline
1. `worktree list --porcelain` → classify each entry: `ours` (ref under `refs/ilvuno/`), `readonly`
   (user branch/detached), `orphaned` (journaled but missing on disk).
2. `doctor`: sections repo / git / ilvuno / config / verification / disk / locks / support; symbols
   `✓ ! ✗ ·`; each `✗` has a `next:` line; no absolute paths; ≤ 60 lines.
3. `doctor --json` emits the same facts as a struct (schema `ilvuno.dev/doctor/v1`).
4. `init`: detect package manager scripts from `package.json`/`Makefile`/`justfile`/`go.mod`;
   propose 1–3 `[[verification.commands]]`; never invent a command that does not exist in the repo;
   write `ilvuno.toml` + ensure `.ilvuno/` in `.gitignore`; refuse to overwrite an existing config.
5. If no runnable command is detected: say so prominently and explain the `unverified` consequence
   (`INT-310`).
6. `init --check` (idempotent dry run) for CI.

## Acceptance criteria
| AC | Statement |
|---|---|
| AC-1 | `doctor` refuses nothing it can fix, and fixes nothing it only reports |
| AC-2 | Every `✗` line has a `next:` command that a reviewer can run |
| AC-3 | `doctor` output contains no absolute paths or env values (`T-SEC-9`) |
| AC-4 | `init` proposes only commands that exist in the repo (asserted by checking the script key) |
| AC-5 | `init` refuses to overwrite; `init --check` is idempotent |
| AC-6 | Worktree classification marks a user worktree `readonly` and never offers adoption |
| AC-7 | `doctor --json` validates against its schema |

## Test commands

## Evidence requirements
Golden `doctor` outputs for: clean repo, sparse repo, no-checks repo. `init` diff on 3 fixture repos.

## Review checklist
- Does `doctor` leak anything (paths, env, identity)?
- Does `init` ever write a command that could surprise the user (e.g. a `deploy` script)?
- Is the "no checks ⇒ unverified" warning impossible to miss?

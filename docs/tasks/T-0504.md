# T-0504 — Corruption handling, cleanup, orphan repair

Milestone: M5 · Estimate: 1.5 d · Owner: B · Provisional: no

## Goal
Handle the states a crash leaves behind: corrupt journals, orphaned worktrees, missing bundles, stale
locks — each with a defined, non-destructive response.

## Dependencies
T-0501, T-0503, T-0202. Architecture `08` §9.

## Allowed file scope
- `internal/journal/repair.go`
- `internal/engine/cleanup.go`, `internal/engine/orphans.go`
- `internal/cli/gc.go` (minimal `gc` for run directories)

**May not touch:** bundle sealing, report rendering.

## Implementation outline
1. Corruption taxonomy implementation: torn tail (tolerate + note), chain break (quarantine + refuse),
   seq gap (refuse), unreadable `state.json` (delete + reproject), missing bundle (approval invalid,
   run readable).
2. Quarantine: move the journal to `journal.corrupt.<ts>` and write a `CORRUPT.md` next to it
   explaining what was found and what is safe to do; never delete.
3. Orphan scan: journaled worktrees missing on disk → `orphaned`; worktrees on disk not journaled →
   report (never auto-delete, because we cannot prove ownership).
4. `gc`: prune settled run directories older than N days with a manifest; never touch bundles by
   default; `--include-bundles` writes tombstones.
5. `repair-orphans` (internal, used by `resume`): remove only `refs/ilvuno/*` + journaled paths.
6. Tests: simulate each corruption by editing files in a settled run; assert the artefact + message.

## Acceptance criteria
| AC | Statement |
|---|---|
| AC-1 | Each of the six corruption classes produces its documented response |
| AC-2 | A quarantine never deletes data; `CORRUPT.md` names what was found |
| AC-3 | An unjournaled worktree is reported, never removed |
| AC-4 | `gc` never removes a bundle by default; tombstones are written with `--include-bundles` |
| AC-5 | `gc --dry-run` is the default behaviour until `--apply` |
| AC-6 | Orphan repair leaves no `refs/ilvuno/*` older than the retention window |
| AC-7 | All of the above is idempotent (running twice changes nothing the second time) |

## Test commands
```
go test ./internal/journal/ ./internal/engine/ -run 'TestCorrupt|TestOrphan|TestGC' -count=1 -v
```

## Evidence requirements
Corruption table (class → detected → response), a `CORRUPT.md` sample, gc dry-run output.

## Review checklist
- Does anything get deleted that we cannot prove we created?
- Is quarantine reversible by a human without the tool?
- Does `gc` default to dry-run?

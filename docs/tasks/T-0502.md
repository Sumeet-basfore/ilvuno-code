# T-0502 — Project lock, idempotency, integrate cache

Milestone: M5 · Estimate: 1 d · Owner: B · Provisional: no

## Goal
One writer per project, duplicate commands that do not duplicate work, and a cache that is safe
because its key is made of SHAs.

## Dependencies
T-0201, T-0205. `REC-105`, architecture `04` §3, `08` §8.

## Allowed file scope
- `internal/engine/lock.go`, `internal/engine/cache.go`
- `internal/cli/lock_flags.go`

**May not touch:** `internal/journal` format, `internal/verify`.

## Implementation outline
1. Lock file `.ilvuno/locks/project.lock` created `O_EXCL` with `{pid, host_id, boot_id, started_at,
   run_id}`; release on all exit paths (defer + signal handler).
2. Staleness: compare `(pid, start_time, boot_id)`; a dead pid on this host ⇒ take over and journal
   `stale_lock_recovered`; unreadable lock ⇒ refuse (never guess).
3. Read-only commands never take the lock (asserted by a test).
4. Idempotency key for `integrate`: `hash(base_sha, sorted source_shas, order, config_digest,
   ilvuno_version, git_version)`; a hit returns the recorded run + exit code, prints the original
   timestamp, and performs zero command executions (counting fixture).
5. `--fresh` forces a new run and records that the cache was bypassed.
6. `verify`/`approve`/`repair` idempotency keys per architecture `08` §8; duplicates are no-ops.
7. Cache invalidation: never TTL-based; only key change. A missing bundle invalidates the entry.

## Acceptance criteria
| AC | Statement |
|---|---|
| AC-1 | A second `integrate` with identical inputs performs zero command executions and < 500 ms |
| AC-2 | Cache hit prints the original timestamp and versions, not "now" |
| AC-3 | A moved ref (new SHA) produces a different key and a real run |
| AC-4 | A stale lock from a dead pid is recovered and journaled; a live lock refuses with the run id |
| AC-5 | Read-only commands work while a run holds the lock |
| AC-6 | `--fresh` bypasses the cache and records that it did |
| AC-7 | A duplicate `approve` creates exactly one approval record |

## Test commands
```
go test ./internal/engine/ -run 'TestLock|TestCache|TestIdempotent' -count=1 -v
make bench SCENARIO=B-22
```

## Evidence requirements
Cache-hit transcript with a counting command, lock race test output, idempotency table.

## Review checklist
- Does the cache key include everything that affects the result (config digest, versions)?
- Can a stale lock cause a permanent refusal? (must be recoverable)
- Is the lock released on panic/interrupt?
- Does a cache hit ever hide that the code changed? (key includes SHAs + config only — document it)

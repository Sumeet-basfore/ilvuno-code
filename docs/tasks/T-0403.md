# T-0403 — Combination-only isolation

Milestone: M4 · Estimate: 1.5 d · Owner: A · Provisional: no

## Goal
Answer the product's central question with a measurement instead of a feeling: does this failure exist
only because the sources are together?

## Dependencies
T-0401, T-0402, T-0202 (worktree creation for per-source runs). `INT-306`, `INT-210`, `M-1`.

## Allowed file scope
- `internal/verify/isolate.go`
- `internal/model/verification_run.go` (add `per_source` field)
- `internal/report/combination.go`
- `docs/combination-only.md`

**May not touch:** the merge loop, the report's verdict logic (this is evidence, not a verdict).

## Implementation outline
1. Trigger: a required command failed on the candidate.
2. For each source SHA: create a throwaway worktree at that SHA, run **only the failing command**,
   capture result, remove the worktree (patch not needed — nothing should change).
3. Compare: all sources pass → `combination_only: true`; any source fails the same command → `false`;
   any per-source run could not complete → `unknown` (never guessed).
4. Cap: ≤ 4 sources per isolation pass (limit), ≤ 1 retry per source on infrastructure error.
5. Record per-source results as evidence with their own `vrf_*`-style subject and logs; record the
   isolation plan in the report.
6. Report section: a compact table (`source | alone | combined`), plus the sentence explaining what it
   means (and what it does not: correlation, not causation).
7. Cost guard: total isolation time capped (default 300 s); exceeding it yields `unknown` with a note.

## Acceptance criteria
| AC | Statement |
|---|---|
| AC-1 | `B-13` yields `combination_only: true` with both per-source logs present |
| AC-2 | A failure that reproduces on one source yields `false`, not `true` |
| AC-3 | A per-source run that cannot complete yields `unknown` with the reason |
| AC-4 | Isolation worktrees are removed even on failure (orphan count 0) |
| AC-5 | The cap (4 sources, 300 s) is enforced and reported when hit |
| AC-6 | The report never says the failure is *caused* by the combination — wording is correlational |
| AC-7 | Isolation adds ≤ 2× the failing command's duration (it runs one command per source) |

## Review checklist
- Is `unknown` the default when evidence is incomplete? (must be)
- Does isolation ever modify a source branch? (must not)
- Is the wording correlational rather than causal?
- Are isolation worktrees journaled like any other (so a crash leaves a defined state)?

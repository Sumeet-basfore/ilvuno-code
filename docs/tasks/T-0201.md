# T-0201 — Journal v1

Milestone: M2 · Estimate: 2 d · Owner: A · Provisional: no

## Goal
An append-only, fsynced, hash-chained record of everything a run did, readable by a human and
by a recovering process, with no database.

## Dependencies
T-0001. ADR-0002, architecture `08` §3.

## Allowed file scope
- `internal/journal/**`
- `schemas/journal.schema.json`
- `docs/journal-format.md`

**May not touch:** `internal/engine` step logic (consumes the API), `internal/evidence`.

## Implementation outline
1. Record struct: `schema, seq, at, run, kind, phase(intent|result|note|uncertain), data, prev, digest`.
2. `Append(rec)`: canonical JSON (sorted keys, no whitespace), `\n`, write, `fsync`. Errors are
   returned, never swallowed.
3. Reader: concatenate segments in order, verify `seq` continuity, verify `prev`/`digest` chain,
   tolerate a truncated **last** line (truncate to last newline, note `torn_tail_recovered`).
4. Roll-over at 32 MiB → `journal.jsonl.1..3`; `seq` continues; a `journal.truncated` note records the
   last retained `seq` when old segments are dropped.
5. `Project(records) State` — a pure function producing the observable state (last settled step,
   pending intents, uncertainties). No caching in the writer.
6. `state.json` writer as an optional rebuildable cache; reader ignores it if absent or invalid.
7. Fuzz target: arbitrary truncation at every byte boundary of a small journal must parse or refuse
   with a typed error, never panic.

## Acceptance criteria
| AC | Statement |
|---|---|
| AC-1 | 1,000 appended records survive a SIGKILL and replay in order with a valid chain |
| AC-2 | A truncated last line is tolerated and noted; a truncated middle line is refused |
| AC-3 | A single flipped byte mid-file is detected as `chain_break` (not repaired) |
| AC-4 | `seq` gaps are refused (`seq_gap`), never renumbered |
| AC-5 | Roll-over preserves continuity across 3 segments |
| AC-6 | Fuzz: 10,000 random truncations, zero panics, 100% typed outcomes |
| AC-7 | Append throughput ≥ 500 records/s with per-record fsync on the CI disk (documented if slower) |

## Test commands
```
go test ./internal/journal/... -count=1 -v
go test ./internal/journal/ -run Fuzz -fuzz=FuzzReplay -fuzztime=30s
```

## Evidence requirements
Fuzz log, a sample journal (5 records) with the chain shown, throughput number.

## Review checklist
- Is every `Append` error propagated (no `_ =`)?
- Does the reader ever "fix" a record? (must not)
- Is canonicalization genuinely canonical (map ordering, float formatting)?
- Does roll-over ever delete a segment that is still referenced by a bundle?

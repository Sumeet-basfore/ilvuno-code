# 12 — Observability

Status: specification. Observability here means "a developer can explain any result to a
colleague without rerunning it" — the local analogue of production observability, with no
telemetry by default.

---

## 1. Goals and non-goals

| Goal | Non-goal |
|---|---|
| Every verdict traceable to a journal record and an exit code | Dashboards |
| Every failure has a stable code and a next action | Remote metrics/APM |
| A run's history is readable a week later, offline | Log aggregation |
| Users can measure their own patterns (`ilvuno stats`) | Product analytics about users |
| Bug reports can carry a complete, redacted reproducer | Crash reporting services |

Aggregate telemetry about *us* is opt-in, counts-only, and specified in doc `09` §8 / `NFR-109`.

---

## 2. The three surfaces

| Surface | Audience | Content |
|---|---|---|
| **Stream** (stderr) | the developer, right now | stage progress, one line per step, terse |
| **Report** (Markdown + JSON) | the developer next week, and a reviewer | the ten sections from doc `06` §9 |
| **Journal** (JSONL) | support, tests, `resume` | intent/result records, authoritative |

They are related but not interchangeable, and none is generated from another's text — report
prose is derived from structured records so a wording change never changes facts.

---

## 3. Stream output

Rules:

| Rule | Reason |
|---|---|
| Progress to **stderr**, results to **stdout** | pipes stay clean (`ilvuno show … \| jq`) |
| One line per step, prefixed `·`, `✓`, `✗`, `!` | greppable, readable in CI |
| No ANSI when not a TTY, or with `--no-color` | logs and CI |
| Never a progress bar | does not survive a pipe; adds nothing |
| `--quiet` = errors only; `--json` = one JSON object on stdout, no progress | scriptability |
| Total stream output for a successful 3-source run ≤ 25 lines | cognitive budget; detail lives in the report |

Shape:

```
· pin      3 sources (base 7c4758d)
· preflight 2 overlapping files, no conflicts
· candidate b7d0f31 (3 steps)
· verify   typecheck ✓ 41s | test ✓ 8m52s
✓ passed  candidate b7d0f31
  evidence .ilvuno/bundles/2026-11-19T14-02-11Z/
  next     ilvuno show --bundle 2026-11-19T14-02-11Z --diff
```

A failure keeps the same shape and adds the diagnosis block from product `04` J-4 — never more
than 15 lines before `next:`. Full output is in the report.

## 4. Report

### 4.1 Section contract

Fixed order; a missing section is a bug, not an omission (`06` §9).

### 4.2 Volatile vs stable

Byte-level determinism (`INT-605`) requires separating the two:

| Stable (byte-identical across runs with same inputs) | Volatile (normalized out of comparisons) |
|---|---|
| SHAs, trees, order, findings, statuses, versions, exit codes | timestamps, durations, paths (they are repo-relative already), host ids |
| manifest digests | journal `seq` of non-semantic notes |
| `not_verified` list | stream-progress artifacts |

`report.json` keeps volatile fields under a single `"run"` object; `Normalize(report)` blanks it;
`DET-1` compares normalized forms. This is how a golden-file test stays useful instead of being
deleted the third time it flakes.

### 4.3 Wording discipline

The banned-claims list (PRD Appendix A) is enforced by a string-table test. Beyond that, three
structural rules:

1. Every verdict sentence names its scope: "these 3 revisions", "these 2 checks".
2. Every claim block is either `verified` (with evidence refs) or `unverified` (with a reason).
3. No sentence in the report is generated by a model when `--interpret` is off; when on, model
   text lives only under `interpretation[]` (doc `06` §7).

## 5. Journal as a debugging surface

`ilvuno show --run <id> --timeline` renders the journal:

```
seq  kind            phase   result
 1   run.planned     intent  base 7c4758d, 3 sources, order A,B,C
 2   base.fetch      result  ok 41ms git 2.43.0
 3   source.pin      result  A=4b825dc B=9f2c4a1 C=c1a9e02
 4   preflight.run   result  2 overlaps, 0 tuple conflicts (merge-tree)
 5   worktree.add    result  .ilvuno/worktrees/irn_…/candidate
 6   merge           intent  i=1 src=4b825dc pre=7c4758d
 7   merge           result  clean post=b7d0f31
 …
14   verify.command  result  test exit=1 18.4s  log logs/14-test.log
15   verify.end      result  failed (1 of 2 required)
16   bundle.seal     result  evb_… manifest sha256:…
```

This is the answer to "why did it say that?" and it is also the artifact a bug report should
attach (with `--redact` on, which is the default).

### 5.1 `ilvuno explain`

```
ilvuno explain <run|finding>
```
Prints, for one finding: which rule fired, the exact inputs (SHAs, paths, command), the evidence
records, and what would have changed the outcome. This is the anti-black-box feature — the
counterpart to `INT-206`'s classification rule.

Example:

```
F-3 check_failed (deterministic, blocking)
  rule      verify.required_failed
  inputs    candidate 9f2c4a1, command "test", exit 1
  compared  payments-intent: exit 0 · fulfilment: exit 0   → combination_only
  evidence  evd_a1 (log logs/14-test.log), evd_a2 (logs/15-test-…)
  would change if: the check were advisory; or one source failed alone
```

## 6. Exit codes and error catalogue

The contract table (doc `01` §6) is enforced by a matrix test: every documented code has a
scenario. Error strings are never the interface.

```
code  class
 0    completed
 1    verification failed / budget exhausted
 2    usage, refusal, environment
 3    conflict or policy block
 4    unverified
130    interrupted
```

Each error has: `code` (stable), `class`, `message` (one sentence, no jargon), `next` (a runnable
command or a decision). The catalogue is a generated table in docs, checked for completeness in
CI (`REC-106`).

## 7. Local metrics

`ilvuno stats` — the user's own numbers, shown to the user first (`07-success-metrics.md` §6):

```
runs            42 (last 30 days)
integrations    31 multi-source · 11 single-source
combination-only failures  3   (9.7% of multi-source runs)
  by pair        payments-intent×fulfilment 2 · api×e2e 1
engine overhead p50 3.8s · p95 6.1s      your checks p50 9m41s
verdicts       passed 24 · failed 5 · unverified 2
not_verified   2 runs had no checks configured
repairs        7 started · 4 succeeded · 3 exhausted budget
```

Why this is observability and not vanity: it shows the user the metric that decides whether the
tool is worth using for them, and it is the same number we would want (`M-1`). Presenting it to
the user first is both honest and the cheapest possible incentive to configure checks.

Data source: `.ilvuno/metrics.jsonl` (append-only, local, derived from journals; deletable).
`--json` for scripting.

## 8. Diagnostics (`doctor`)

`doctor` is the support surface, and it must be safe to paste into an issue.

```
ilvuno doctor
✓ repo        main, worktrees 1, shallow=false
✓ git         2.43.0 (≥2.38 merge-tree ok)
✓ ilvuno      0.1.0 (darwin/arm64)
✓ config      ilvuno.toml digest sha256:…, 2 required + 1 advisory command
! verification no index_command (interface analysis limited)
! disk        12.4 GiB free in .ilvuno (2 runs retained)
! locks       stale lock from irn_… (pid 4123 gone) — will be recovered on next run
✗ support     sparse checkout active → integrate refuses (repo_sparse)
  next: git sparse-checkout disable
```

Rules: no paths outside the repo, no env values, no refs of other repos, no user identity. A test
asserts `doctor` output on a corpus of fixtures contains no value matching the redaction classes
(`T-SEC-9`).

## 9. Performance budgets as observability

Instrumented and asserted in CI, so regressions are caught by tests rather than by users:

| Metric | Budget | Where asserted |
|---|---|---|
| Engine overhead (excluding commands), 3 sources / 50k files | ≤ 5 s p50 (`NFR-102`) | `bench` job on the large fixture |
| Pin + preflight | ≤ 800 ms | benchmark |
| Candidate build (3 merges) | ≤ 1.5 s | benchmark |
| Report render | ≤ 150 ms | benchmark |
| Binary size | ≤ 25 MiB | release job |
| Peak RSS, 50k files | ≤ 250 MiB | benchmark |
| Cold start (`--version`) | ≤ 30 ms | benchmark |

A budget failure is a visible red test, not a silent drift. If a budget cannot be met, the budget
changes in a reviewed diff with a reason — the same discipline as a schema change.

## 10. What we deliberately do not log

| Never logged | Why |
|---|---|
| Env var values | `INV-13`; only names + hash |
| File contents outside a log the command printed | privacy and size |
| Provider raw frames (MVP: none; post-MVP: rotating diagnostic only) | size + leakage (`T3-016` caps at 64 KiB for this reason) |
| User identity beyond a label they choose | `INV-9` |
| Absolute paths | `INV-9` |
| Anything from `~` outside `.ilvuno/` | out of scope by design |

## 11. Support workflow (how a bug report actually happens)

```
1. user: ilvuno explain <finding>            → understand
2. user: ilvuno doctor                       → environment
3. user: ilvuno show --run <id> --timeline   → what happened
4. user: ilvuno bundle export --run <id>     → redacted bundle, attached to the issue
5. maintainer: ilvuno bundle verify <path>   → confirm integrity offline
6. maintainer: run the same spec against the fixture forge
```

Step 6 is the design pressure that keeps fixtures small and the CLI scriptable: if a reported
scenario cannot be reproduced with `forge` + one command, the report is incomplete.

## 12. Open questions

| ID | Question | Recommendation |
|---|---|---|
| `OB-1` | Structured logs (`slog`) or plain lines? | Structured internally, rendered to lines; `--json-logs` for support |
| `OB-2` | Ship a `debug` subcommand bundling doctor+timeline+bundle? | Yes, one command, when support volume justifies it (post-v0.1) |
| `OB-3` | Should `stats` be shown on every run? | No: one line in the report, full view on demand. Recurring nags are the fastest way to be ignored |
| `OB-4` | Retention for `metrics.jsonl`? | 12 months, local, prunable with `gc` |
| `OB-5` | Do we need tracing spans? | No: a 6-minute local pipeline with ~50 journal records does not need distributed tracing; `seq` is the trace |

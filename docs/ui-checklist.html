Ilvuno — UI completion checklist

This is the working plan for finishing the window. It is not a report: it changes as work lands.

How a milestone moves: implement the smallest complete thing → run the checks → look at the real window → fix → commit → tick the boxes here. A box is ticked only with evidence: a test name, a measured number, or a screenshot path.

Where the rules come from:

  • docs/prd.md — what v0 must prove, and the non-goals.
  • research/13-ui-anatomy.md — the layout, taken from Cursor, Codex and Vibe Kanban screenshots.
  • research/01-t3code.md, research/02-orca.md — how the two reference apps organise the same work.
  • AGENTS.md — no PTY agents, no scheduler, no cloud, no multi-user in v1.

1. What is approved, and what is not

The goal was to make the window complete, using T3 Code and Orca as references. A reference is not an approval: these two apps ship whole subsystems that Ilvuno's own docs leave out of v1. Building them would break docs/prd.md §6 and AGENTS.md. So they are listed, not built.

Approved — in the PRD, the data model or the roadmap

Area What Where it is already promised
Left Threads as agent sessions, grouped by state, per run docs/prd.md §4
Left Run switching; project shown from the goal base docs/data-model.md
Left Search across runs, threads, actions palette
Centre The conversation: prompt, what the agent said, its report, files docs/prd.md §4
Centre A composer that sends a message task, with no file scope data-model.md, migration 0005
Centre Live updates, errors, a stopped run with its reason docs/api.md (SSE)
Right Board, checks, gate, artifacts, thread list docs/prd.md §5
Right Accept or send back at the gate, with a note docs/prd.md §5
Settings Theme, agent detection with safety, budget defaults, message policy, human gate docs/prd.md §5

Not approved — do not build without the user's word

Asked for in the goal Why it is not approved What would make it approvable
Git worktrees, branches, commits, diffs, PR creation, merge controls v1 has one branch and a runner-executed merge at the gate. AGENTS.md: "Let an agent's shell touch main" is a do not; per-thread worktrees are roadmap stage 2 Roadmap stage 2 written into the PRD, with conflict rules
An in-app terminal / PTY AGENTS.md: no PTY agents in v1 (orca carries 45 hand-tuned records for it) A decision reversing D2 in research/07-decision.md
File explorer and file viewer Not in the PRD. Artifacts are listed today; reading them is a different feature A PRD line and a security note (reading arbitrary project files)
Attachments (files, images) in the composer Providers take text today; attachments need a per-provider path Provider contract change
Per-message model and reasoning-effort pickers The agent is chosen per thread at goal time; per-message model choice is not in the PRD A PRD line. Until then the CLI's own default applies
Changing a thread's agent mid-run The thread's agent is fixed when the run starts Treated as M4 below — small, and it is the product's point
Multiple projects side by side One run belongs to one project; the rail switches runs, not projects A PRD line

Nothing above is silently dropped: each is either a milestone below or a question in §5.

2. Milestones

Status: done · next · blocked (needs a decision) · later (approved, low value now)

M0 — The thread-first shell · done

  • [x] Threads grouped Needs you / Working / Done, from real run state
  • [x] Selected thread's conversation in the centre, newest turn at the bottom
  • [x] Composer sends kind:"message"; the board does not move (test: a_message_needs_no_scope_claims_no_board_entry)
  • [x] Board keeps a full view (#board)
  • [x] Settings: General, Agents, Defaults, About
  • [x] 11 screenshots at 1440×900 in crates/desktop/shots/, from a real run
  • Evidence: commit cf3a083, cargo test --workspace → 130 passed
  • Known: gate.png comes from an older run with a gate open; the demo run is accepted

M1 — The run's facts, in the rail · done

The v3 shell showed project, run id, duration, rounds, tokens and a budget bar. v4 dropped them. All of these are real fields on GET /runs/:id; none need new data.

  • [x] A Run section above Board in the right rail: folder, run id, how long it has run, rounds used against the cap, tokens used against the cap, and a bar
  • [x] Every number comes from the API. No spend in dollars — the engine records no cost (v3's $0.12 was invented)
  • [x] A missing value renders —, never 0
  • [x] The folder keeps its leading slash on short paths (/tmp/stop2, not tmp/stop2)
  • [x] Fits at 1440; at 1280 the rail folds and opening it shows the same block, with no sideways scroll
  • Evidence: commit 4c2adfe; shots/threads.png shows the block against run 6ba693b9, whose API answers 362211 tokens of 600000 in 2 of 3 rounds — the same numbers on screen

M2 — Stop a working run · done

A run could only be stopped by waiting for it to stop itself. A person watching a bad round had no move.

  • [x] POST /runs/{id}/stop: the turn in flight finishes, no new task or round starts, status human_paused, reason stopped by you
  • [x] The status change is journaled in one transaction with the projection (run.stop + run.transition)
  • [x] A Stop button in the topbar while the run is working; its tooltip says what happens
  • [x] The banner says who stopped it and offers Resume
  • [x] Resume works — it did not before: drive_with now reopens a stopped run before the loop reads it
  • Evidence: commit 40d1009; cargo test --workspace → 133 passed, including stopping_a_run_pauses_it_and_keeps_the_reason, a_finished_run_cannot_be_stopped, a_stopped_run_can_be_resumed. Stopped a real run 8s in (12 shell sections): the turn finished, the task finished as reported, the round stayed open, and shots/stopped.png is that screen.

M3 — New run from a goal file · done

The New run dialog only took pasted JSON. People keep goals in files.

  • [x] A Goal file row: type a path and press Open, or press Browse… for the system picker
  • [x] The picker returns a path; a command reads it (the page has no file access), capped at 1 MiB
  • [x] A path that does not exist, or a file that is not JSON, shows the reason and starts nothing
  • [x] A loaded goal starts a run
  • Evidence: commit d7b4a22; shots/new-run-file.png is the dialog with examples/board-experiment.json loaded. The GTK picker opens as its own window and returns a path. Tauri 2 refuses it without capabilities/default.json (dialog.open not allowed), which is why that file exists
  • Limit: driving the picker with xdotool type puts a typo in the location bar now and then; that was automation, not the app

M4 — Choose the agent for a thread · done

The product's claim is "agents are choices". The choice was made once, in the goal file.

  • [x] The thread header opens a list of the agents the run's goal names; the picker sets the next task
  • [x] Refused: an unknown thread, an agent the goal does not name, a thread with a turn in flight, a finished run — each with a reason the window shows
  • [x] The journal records thread.agent with from, to and who chose
  • [x] A note when every thread runs on one agent: it works on one subscription, and a second agent is the point
  • Evidence: commit d36828b; 136 tests, including a_thread_can_move_to_another_agent_and_the_journal_names_both, a_thread_with_a_running_turn_keeps_its_agent, the_agent_of_a_thread_can_be_changed. Live check on a run naming claude-main and codex-acp: switched checker, the API showed claude-main, the journal showed {"from":"codex-acp","to":"claude-main","by":"user"}, shots/agent-picker.png is the menu
  • Found: the menu was hidden under the button's own native tooltip — it looked like an empty grey box. The button carries aria-label now and no title

M5 — What the agent actually ran · blocked

The conversation shows the agent's words and its report. It does not show the tools it called. Codex and Cursor both show this, and it is the first thing people look for when a run fails.

  • Not approved yet: the runner records results, not tool events. Streaming them means a provider-contract change (Claude tool_use, ACP session/update).
  • Decision needed: is a read-only activity list in v1, or does it wait?

M6 — Reachability and scaling · done

  • [x] Keyboard: focus draws a 2px accent ring at 5.5:1; after 14 Tabs inside settings the ring is still inside the dialog, so the trap holds; Escape closes
  • [x] Text contrast measured on the real tokens, both themes: body 15.6 / 15.1, board text 7.1 / 6.8, labels 4.9 / 5.5, accent 5.6 / 5.5, accents on their weak surfaces 6.0-6.9 — all ≥ 4.5:1
  • [x] Control boundaries (composer, note box, inputs, switch, buttons) moved to --control-line at 3.25:1 dark and 3.67:1 light. Hairline dividers stay at 1.2-1.5:1: WCAG exempts decoration, and they are not the only cue for anything you can use
  • [x] No clipping at 1440, 1280, 1060 or 960 (the window's minimum); the rail folds at 1280
  • [x] 200%: with GDK_SCALE=2 the layout stays readable, since the page is laid out in CSS pixels
  • Evidence: commit 9541b44; screenshots taken at each width while checking
  • Found: a CSS-only edit rebuilt nothing — tauri::generate_context! embeds ui/, and the build script did not watch it. Fixed, so a stylesheet change now reaches the window

M7 — Every state says what it is · done

  • [x] No runs, no tasks, waiting, paused, token budget spent, offline: each states the cause and what to do next, or says plainly that there is nothing to press
  • [x] A run whose round closed with nothing queued says waiting, not working: the engine is right, the window was not
  • [x] A spent token budget offers no Resume button, because pressing it would do nothing
  • [x] A failed round no longer draws each failing check twice
  • Evidence: commits d58ec15, d7b4a22; shots/states/{no-runs,offline,paused,waiting,budget}.png, each from a real state. The paused and budget ones came from real runs: paused by POST /stop, budget by a goal with two tasks and a 1,000-token budget (it spent 63,274)
  • Not shown: blocked and no_progress need an orchestrator and two failing rounds. blocked is only reachable when the runner cannot create the orchestrator's wake-up task, and no_progress needs the same checks to fail twice. Both share the banner verified above, but neither has a screenshot

M8 — Settings that stick, or say why not · done

  • [x] A failed PUT /settings shows the reason inline and puts the old value back: typing 0 into Rounds gives "budget_rounds must be 1-20" with the field back at 3, and the API unchanged
  • [x] A valid change persists: 5 → GET /settings says 5
  • [x] An error does not outlive the edit: opening the panel clears it and re-reads the runner
  • [x] Each setting names its effect in one line
  • Evidence: commit 9e99bb8; shots/settings-error.png

3. How to verify

RUSTUP_TOOLCHAIN=1.100.0 cargo test --workspace          # 130 tests today
ILVUNO_HOME=/tmp/demo-real ./target/debug/ilvunod &      # the runner the window reads
tools/shot.sh /tmp/check.png 1280 900                    # one shot at a width (opens a real 1280 window)
tools/shots.sh                                           # the full set into crates/desktop/shots/

The window's HTML, CSS and JS are compiled into the binary (frontendDist), so an edit needs cargo build -p desktop before it can be seen. tools/shot.sh does that for you.

5. Known limits

  • "Ran for" keeps counting while a run is paused or at the gate, because the engine has no end time for those states. It is honest for a finished run and generous for a paused one.
  • A goal whose threads all name one agent is allowed, and the rail says so. Nothing stops it.
  • gate.png is an older run with a gate open; the demo run is accepted.

6. Open questions for the user

  1. Tool activity in the conversation (M5). In or out of v1? It needs a provider-contract change.
  2. Git (worktrees, branches, PR, merge). Roadmap stage 2, and the biggest single piece of the reference apps. Approve it as the next stage, or keep v1 to one branch and the gate?
  3. A terminal. AGENTS.md says no. Reference apps all have one. Confirm it stays out.
  4. Cost. The engine records tokens, not money. Should it record a per-call cost cap result, so the rail can show spend honestly?
